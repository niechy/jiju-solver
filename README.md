# jiju-solver

《无悔华夏》集句（唐诗集句）玩法的**离线规则模拟 + 策略规划/评估**工具包。

它回答两个问题：

1. **这个局面里，下一步该选哪句 / 该不该刷新？**
2. **这套规则、这套权重、这套规划器，长期期望到底有多好？**

它**不含任何游戏交互**。输入是「玩家当前可集句诗句池与资源状态」的 JSON，输出是动作与期望评估；纯离线、确定性（只由种子决定）、无网络。

- 规则模型与算法细节：[docs/algorithm.md](docs/algorithm.md)
- 被实测否掉的方向与引用数字时的陷阱：[docs/failures.md](docs/failures.md) ← **先读这个**

---

## 这是什么（以及不是什么）

| | |
|---|---|
| ✅ 是 | 合格池推算（`EligibleVerseIDs` / `RemainingPool`：由账号解锁快照算出真实可抽池）、集句规则的确定性模拟器（`World`）、可精确求解的小残局求解器（`ExactMulti`）、蒙特卡洛规划器（`MultiRollout`）、权重进化搜索（`TrainContinuation`）、一套可复现的配对评测口径 |
| ❌ 不是 | 游戏客户端、自动化脚本、存档工具；不含任何联网行为 |
| 输入 | 一个 JSON：合格诗句池 + 经济状态 + 当前候选（见下） |
| 输出 | 动作选择、每个合法动作的期望回报与配对误差、精确解（小池） |

关键建模主张只有一条：**可抽池是「已解锁且尚未收集」的真实合格池，且随收集单调缩小。** 这条与早期实现差异最大，也是本项目存在的理由（见 [先例与致谢](#先例与致谢)）。

## 规则简述

每轮给出一句「上一联」（`prev`）与 3 个候选，选一句接上；不满意可以**刷新**重抽。每句诗带三个属性组：

| 判定 | 条件 | 效果 |
|---|---|---|
| **押韵** | `prev.Group1 ∩ cand.Group1 ≠ ∅` | 灵犀 **+7** |
| **中间态** | 主韵组无交集，但 `Group3` 有交集 | 无奖惩 |
| **出韵** | 主韵组与副韵组都无交集 | **连续 2 次 → 每轮入场费永久 +1** |
| **相粘**（独立维度） | `Group2` 不同（李贺句恒相粘） | 灵犀 **+2**；否则诗意 **−5** |

其余规则：

- 进入一轮扣 `cost` 灵犀；抽 3 句（池不足 3 句时抽到 1~2 句也能选）；
- **刷新**：先用免费次数，免费次数用完后每次花 1 灵犀；免费额度**每轮重置**（诗人首收抬高的是上限）；
- 刷新的语义是「本轮内重新抽 3 句，已展示过的句子本轮不再出现」，**未选中的句子下一轮回到池中**；
- **中间态不清空连错标记**（默认 `MiddleClearsRun=false`）→ 出韵→中间态→出韵仍会涨价。这是敏感性开关，规则依据见 [algorithm.md](docs/algorithm.md#13-回合结算与费用)；
- 诗句可能自带灵犀（+2/+5）与诗意（+10/+20）；**诗人首次收集**触发该诗人的奖励（温庭筠/鱼玄机送免费刷新 +1，孟浩然/常建/贾岛/刘长卿/孟郊 +10 灵犀，韦应物 +5，李贺 +30 诗意）；
- **结束条件**：灵犀 < `cost`，或剩余合格句不足。

**决策目标**：**先最大化诗意，再最大化集句句数**（字典序，`shiyi-first`；并列时比句数）。

## 算法简述

1. **合格池推算** — `EligibleVerseIDs(词库, UnlockState{账号大臣/国家在任大臣/已激活政策})` 按每句诗的解锁条件算出可抽集合，`RemainingPool` 再排除已收集的句子。这一步不能省：池子是什么，决定问题是什么。
2. **`World`** — 确定性规则模拟。`Legal` 判合法、`Step` 结算并抽下一批、`AfterState` 只应用**确定性效果**而不抽签（Q 分解 `Q(s,a) = 即时 + E[抽签后的价值]` 的载体）。
3. **线性候选价值函数** — `net 灵犀 × NetGainWeight + 诗意 × ShiyiWeight + 押韵分 + 相粘分 + 中间态分 − 出韵罚 + 新诗人分 + 换组项`。权重来自进化搜索（`EvolvedStrategy()`）。
4. **`BaselineAction`** — 续跑策略：取分最高的候选 + 一个刷新判据。
5. **精确一步最优停止**（当前默认刷新规则）— 用**真实未屏蔽池**（未收集 ∩ 本轮未展示 ∩ 非当前候选）上的**精确次序统计量**算「重抽后的期望最优分」，再与「接受眼前最好」比较：

   ```
   E[max] = Σ_i s₍ᵢ₎ · C(i−1, k−1) / C(|R|, k)       k = min(3, |R|)
   刷新 ⟺ E[max] − 刷新成本 > 当前最优分 + StopMargin
   ```
   1 灵犀按 `NetGainWeight` 换算成分数单位。这一步取代了原来手写的三段硬门控 + 两道收益闸，**权重一个都没动**。
6. **两步最优停止**（`StopDepth=2`，已实现、**非默认**）— 多加一层「再刷一次的期权」：`V₂ = Emax(P) + E[(K − maxS)⁺] ≥ Emax(P)`。
7. **`MultiRollout`** — 对每个合法动作用续跑策略做配对蒙特卡洛 rollout，含独立随机数流上的续跑策略筛选与两阶段采样。
8. **`TrainContinuation`** — 权重向量的短程进化搜索，搜索流与验证流分离，只有验证集上 `delta > 2.4×SE` 才采纳（2.4 ≈ 3 次比较的 Bonferroni 门槛）。
9. **`ExactMulti`** — 小残局的精确期望解：穷举所有等概率候选集并记忆化，返回向量回报；不完整的搜索不暴露任何部分推荐。

## 实测结果（头条）

> 口径：全部为**离线模拟器内**的配对整局实验，初始快照为合格池 70 句 / 已集 `{3,110}` / 灵犀 41 / 入场费 8 / 免费刷新 1 / `prev=110`，目标 `shiyi-first`，两侧同为 128 根采样 + 32 续跑筛选采样。「诗意 / 句数」都是**本局新增**的增量。

**① 精确一步最优停止（默认刷新规则）**

同一份冠军权重、同一快照，唯一改动是 `ExactStopRefresh: false → true`：

| 指标 | 三段硬门控 | 精确一步最优停止 | 配对差 / 约 95% 区间 | t |
|---|---:|---:|---|---:|
| 诗意 | 473.675 | **528.400** | **+54.725 [38.561, 70.889]** | +6.64 |
| 句数 | 43.330 | **49.155** | **+5.825 [4.179, 7.471]** | +6.94 |

> n = 200 配对整局，种子 42。**独立留出集复刻**（两个未用于训练/调参的种子，权重未做任何调参）：种子 202609401（n=400）**+59.95 ± 11.86**、种子 202609402（n=200）**+49.83 ± 16.52**；合并 **n=600：+56.58 ± 9.64 诗意（t = +11.7）/ +5.96 句数**。

**② 两步最优停止（非默认）**

| 种子 | n | 诗意（一步 → 两步） | 配对差 | 2SE | t |
|---|---:|---|---:|---:|---:|
| 42 | 200 | 533.100 → 550.525 | +17.425 | 16.810 | +2.07 |
| 202609401 | 200 | 550.350 → 558.525 | +8.175 | 15.890 | +1.03 |
| 合并 | 400 | — | **+12.80**（反方差加权 +12.54） | 11.56 | **+2.21** |

方向一致，但 **t ≈ 2.17、只有两个种子 ⇒ 未确立**；且它把付费刷新抬高约 20%，其中一部分来自一个已知近似（再刷时的池被当成完整池，**高估**期权价值）。因此保留但**不默认开启**。详见 [failures.md §6](docs/failures.md#6-两步最优停止)。

**③ 小残局的精确可解规模**（`ExactMulti` 实测，串行）

| 池 | 节点数 | 墙钟 |
|---:|---:|---:|
| 6 | 892 | 8 ms |
| 7 | 6,631 | 67 ms |
| 8 | 54,099 | 0.73 s |
| 9 | 318,637 | 6.9 s |
| 10 | 1,781,446 | 82 s |

每加一句池约 ×5.6~8.1。真实局面池规模是 20（残局）/ 68（标准态）/ 572（全库），**精确在线求解不可行**——它只用于小残局与建模校验。默认 `ExactLimit = 6`；抬到 8 仍在 1.5 s/决策预算内，再往上不划算。

**④ 一个反面参照**（历史口径，另一个模拟环境，**不可与上面并列比较**）：进化搜索学权重相对手调基线 125.76 → 149.92 句（+19.2%），而把「进化权重 + 精确刷新 EV」**叠加**反而退步到 137 —— 各方向不是可自由叠加的积木，见 [failures.md §8](docs/failures.md#8-把进化权重与精确刷新-ev-叠加)。

## 怎么跑

命令行入口按功能拆成四个（`cmd/` 下的子命令），**参数以各自的 `-h` 为准**：

```powershell
# 模拟与评测：跑整局，出均值 / 分位数 / 配对区间
go run ./cmd/sim -h

# 权重搜索：在给定池与经济状态上进化搜索续跑权重
go run ./cmd/optimize -h

# 单状态求解：对给定局面给出每个合法动作的精确期望（只适合小池）
go run ./cmd/solve -h

# 对比：两个策略 / 两个池口径在同一种子下的配对对照
go run ./cmd/compare -h
```

四个入口共享一组「局面」参数：`-lib`（词库路径，默认 `data/verses.json`）、**`-unlock`**（账号解锁快照，据此算出真实可抽池）、`-poolsize`（未给 `-unlock` 时从词库随机切一个池，默认 70；`<=0` 用整库）、`-cost` / `-lingxi` / `-free` / `-first`。各自再叠加功能参数：`sim` 的 `-episodes` / `-rollout` / `-samples`，`optimize` 的 `-seconds` / `-generations` / `-population` / `-validation` / `-out`，`solve` 的 `-limit` / `-maxnodes`，`compare` 的 `-strategy-a` / `-strategy-b` / `-rollout-b`。

**推荐始终带上真实解锁快照**，否则跑的是「从词库随机切池」的合成口径：

```powershell
go run ./cmd/sim -unlock data/unlock-example.json -episodes 2000
```

库本身可以直接用（module `jiju-solver`，Go 1.26）：

```go
lib, err := jiju.LoadLibrary("data/verses.json")       // 573 句
w, err := jiju.NewWorld(lib, jiju.DefaultWorldRules())

// ① 由账号解锁快照算出真实合格池 —— 这一步不能省
eligible, err := jiju.EligibleVerseIDs("data/verses.json", jiju.UnlockState{
    AccountMinisters: map[int]int{13: 3, 16: 2, 41: 1},
    CountryMinisters: map[int]int{217: 2},
    ActivePolicies:   []int{2467, 2468, 2469},
})
pool := jiju.RemainingPool(eligible, collected)

// ② 局面由调用方提供
st, err := w.Start(jiju.WorldStart{
    PrevID: 110,
    Collected: []int{3, 110},
    Eligible: pool,                                    // nil = 全库（仅压力测试）
    Lingxi: 41, Cost: 8, FreeLimit: 1, FreeRemaining: 1,
}, rng)

// 单步动作（默认策略）
act := w.BaselineAction(st, jiju.DefaultStrategy())

// 目标感知的配对 rollout（诗意优先）
res, err := w.MultiRollout(ctx, st, jiju.DefaultRolloutOptions(),
    jiju.VerseObjective{Priority: "shiyi-first"})

// 小残局精确解（池 ≤ ExactLimit 时自动被 MultiRollout 采用）
exact := w.ExactMulti(ctx, st, 6, 100000, jiju.VerseObjective{Priority: "shiyi-first"})
```

跑测试：

```powershell
go test ./...
go vet ./...
```

## 失败案例与引用纪律

这个项目的**大部分工作量花在否掉方向上**，而引用数字时最容易犯的错也都记录在那里：

- 假定整库可抽（先例实现的局限）为什么不是「按比例缩放」就能修的；
- 状态价值函数回归、深度≥2 前瞻、非线性概率特征、集合条件化 critic 为什么都没打赢；
- 两步停止、动作条件策略筛选、终局修复、两步搜索的实测数字为什么都不足以采纳；
- 「进化权重 + 精确刷新 EV」叠加为什么反而退步；
- 一个**被时间预算截断的搜索结果被永久缓存**的真实 bug（机制 + 修复）；
- 以及最重要的方法论警告：**±2SE 只覆盖一个状态，会低估跨状态不确定性 12~32 倍**（实测跨状态 sd = 48.86）；比较次数多，**孤立的 t≈2 不能信**；参考臂换了同一个改动能从 +1.755 变成 +14.405。

→ **[docs/failures.md](docs/failures.md)**

## 已知局限

1. **规则模型是推断的，不是实测的。** 刷新语义（本轮内无放回 + 未选句下轮回池）与「中间态不清空连错标记」都按属性组配置推断并显式建模，未做逐项运行时核对；后者保留为 `MiddleClearsRun` 敏感性开关。
2. **候选均匀抽样是模型假设**，不是对真实抽签分布的测量。
3. **所有数字都在模拟器内**，没有真实客户端表现；本文档不声称任何真实环境收益。
4. **单快照验证为主。** 多数评测只在一个合格池、一个初始状态上做，±2SE 不含状态间方差；跨池普适性**未被验证**。`CountStrategy` / `AdaptiveStrategies` 的存在本身就说明策略是状态相关的，只在一个池上验证可能高估或低估普适性。
5. **`TrainContinuation` 的完成度缺口**：搜索被时间预算截断时循环只 `break`，外层 `ctx` 仍能跑完验证，于是 `Accepted` 可能为 true 而 `Generations < 请求代数`。本包不含缓存层，因此不会固化；**上层加缓存/落盘必须校验完成度**（见 [failures.md §9](docs/failures.md#9-被预算截断的搜索结果被永久缓存)）。
6. **`ExactLimit` 只能覆盖小残局**（池 ≤ 6，可安全抬到 8）。真实池规模下的精确求解不可行。
7. **进化权重的历史成绩来自另一个模拟环境**（口径不同，不可与本文其他数字并列）。当前 `data/verses.json` 下的 573 句库与历史快照也不完全同源。
8. **未做的方向**：17 维线性权重与非线性项的联合搜索、跨合格池的正式留出验证、按 `(池, 灵犀)` 二维门槛触发精确解。

## 先例与致谢

本项目的起点是 [2233-123/-_wuhuihuaxia_verse](https://github.com/2233-123/-_wuhuihuaxia_verse)：一个用 `skopt.gp_minimize` 做 7 维贝叶斯优化（`BayesianOptimization.py`）、再用 `MonteCarloSimulation.py` 做蒙特卡洛统计的实现，数据来自其清洗后的 `Verse_clean_updated.csv`。它建立了「押韵链主导 + 换组阈值 + 诗人券/爆款收益抢夺」这套策略骨架，本项目沿用其中若干思想（换组阈值、目标大组偏好、灵犀兑换、免费刷新券抢夺）。

它的 README 自己写明了本项目要修的那条局限：

> 实验预设诗句库中的所有诗句都是可收集的，且出现概率相等，这可能与实际游戏不符

这个假设会直接改变问题的**期限**：在该假设下，其部分预设的平均集句数达到 559.58 句、P95 = 573 句（即整库被收完）；而在真实的合格池（约 70 句，且随收集缩小）下，一局是**资源受限**而非池受限的。把在一个池上拟合好的权重直接搬到另一个池形状上，实测代价是 **−46.807 句（[−48.867, −44.747]，n=3000）**。因此本项目的核心差异是：**把真实合格池作为一等输入**（`WorldStart.Eligible`，随收集收缩），并在其上做规划与评测 — 见 [failures.md §1](docs/failures.md#1-假定整库都可抽)。

该项目的数据是公开的，本项目**不重新分发**它的任何数据文件；`data/verses.json` 的字段结构（`Group1/Group2/Group3`、`EffectTypeList` 等）沿用同一套属性命名，便于对照。
